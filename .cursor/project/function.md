# 好友关怀「非实时」同步 + 本地后续提醒（function 说明）

> 文档类型：方案说明（非已实现代码）。范围：Flutter + backend；不含 `web/`。

---

## 1. 产品目标（要解决什么）

- **不依赖**远程推送（FCM / 极光 / APNs）时，让用户在**打开 App 并登录后**，能知道**好友是否在最近提醒过自己喝水/发关怀**。
- 若有未处理的「来自好友的关怀」，在本地**排程 1～2 天内的轻量通知**（非实时、可错开文案），**提高回访**，而不是冒充「对方此刻正在响你手机」。

---

## 2. 功能细节（建议行为）

### 2.1 触发时机

| 时机 | 行为 |
|------|------|
| **冷启动 / 登录成功** | 调用后端 **拉取「我收到的、未读/未消费的关怀列表」**（或「自上次同步以来」的增量）。 |
| **从后台回前台**（可选） | 节流（如 ≥5 分钟一次）再拉一次，避免过于频繁。 |

### 2.2 拉取结果后的客户端逻辑

1. **持久化**：写入本地（如 Hive / SharedPreferences）  
   - `lastSyncedAt`  
   - `pendingCareItems[]`：`{ id, fromUserId, nickname, message摘要, createdAt, consumed? }`  
2. **若存在未读条目**：  
   - 更新 **心连心** UI（角标 / 列表）。  
   - **调度本地通知**（`flutter_local_notifications` 已具备能力）：  
     - **当天晚些时候**一条（例如用户 `bedTime` 前 1 小时，或固定 20:00，可配置）。  
     - **次日**一条（文案不同，偏「回顾/别忘记喝水」）。  
     - **第三日可选**一条弱提醒或不再打扰（产品定）。  
3. **用户在心连心点开/已读**：  
   - 标记 `consumed`，**取消**尚未触发的、与该批关怀绑定的后续本地通知（需固定 notification id 槽位或按 batchId 管理）。  

### 2.3 文案策略（「一两天不太一样」）

| 阶段 | 示例方向（需产品定稿） |
|------|------------------------|
| **首日（拉取当日）** | 「{昵称} 今天向你发来了喝水问候，去心连心看看～」 |
| **次日** | 「昨天好友惦记你喝水，今天也记得达标哦～」 |
| **第三日（若仍未读，可选）** | 「心连心还有未读关怀，点进来看看」或停止推送避免骚扰 |

注意：**诚实话术**——不写「对方正在叫你」，避免与实时推送混淆。

---

## 3. 优点

| 优点 | 说明 |
|------|------|
| **工程成本低** | 无推送证书、无 FCM/极光控制台；复用现有 HTTP + 本地通知。 |
| **全平台一致** | Android / iOS / macOS / 桌面均可「打开 App 拉数据」；本地通知在各端已有基础能力（以插件支持为准）。 |
| **服务端可控** | 未读状态、频控、防刷可在后端统一做。 |
| **与现有架构贴合** | 后端已有 `/api/care` 与联系人；需**新增**「收到关怀」的数据模型与接口（见下文可行性）。 |

---

## 4. 缺点与风险

| 缺点 | 说明 |
|------|------|
| **非实时** | 对方发送后，接收方**只有打开 App 后**才可能看到并触发后续本地排程；锁屏**不会**立刻出现「好友刚发」的强感知。 |
| **依赖再次打开** | 若用户长期不打开 App，关怀一直堆积在服务端，直到某次打开才「突然一堆」——需列表与聚合展示。 |
| **本地通知可被系统限制** | 省电、厂商策略可能导致**非精确**触发；与现有喝水提醒同一类限制。 |
| **与「定时喝水提醒」抢 ID / 频道** | 需为「关怀回访」预留 **独立 notification id 区间** 与 **独立 Android channel**，避免与 `scheduleReminders` / 自定义提醒冲突。 |
| **多设备** | 同一账号多机登录时，「已读」需以**服务端为准**同步，否则重复通知。 |

## 5. 技术可行性

### 5.1 后端（当前仓库：**需新增**，尚无「收到关怀」实体）

| 项 | 可行性 | 说明 |
|----|--------|------|
| **数据模型** | **需加** | 例如 `CarePing` / `FriendCareMessage`：`id`, `fromUserId`, `toUserId`, `message`, `createdAt`, `readAt?`（或 `consumedAt`）。 |
| **API** | **需加** | `GET /api/care/inbox?since=...` 或 `GET /api/care/inbox/unread`；`POST /api/care/inbox/:id/read` 标记已读。 |
| **发送路径** | **需加** | 发送方在 App 内「发关怀」时，除本地外 **POST** 创建一条服务端记录（否则收件箱永远为空）。 |
| **与现有 care 关系** | 可复用 | `CareContact` 校验「仅联系人可发」；限流与鉴权沿用 `auth` 中间件。 |

**结论**：**可行**，工作量集中在 **Prisma 迁移 + 2～3 个路由 + 发送端改造**。

### 5.2 Flutter 客户端

| 项 | 可行性 | 说明 |
|----|--------|------|
| **登录后拉取** | **可行** | `BackendApiService` 在 `ensureAuthenticated` 或 `MainShell` / `HeartProvider.load` 后增加 `syncCareInbox()`。 |
| **本地排程** | **可行** | `NotificationService` 已有 `zonedSchedule` / `scheduleCustomReminder`；可封装 `scheduleCareFollowUpNotifications(batchId, …)`，使用**固定 id 段**（如 `9100–9109`）便于取消。 |
| **取消已读** | **可行** | `cancelReminder(id)` 已存在；需在「已读」时批量 cancel 对应 batch。 |
| **文案分天** | **可行** | 根据 `DateTime.now()` 与首次调度日期，在排程时写入不同 `body`。 |

### 5.3 与「仅本地心连心」的兼容

- 现状：`HeartProvider` 以 **SharedPreferences** 存关怀记录，**无服务端**。  
- 落地本方案后：建议 **服务端为真相源**，本地缓存做离线展示；或 **过渡期** 双写（复杂度高，不推荐久留）。

---

## 6. 实现优先级建议（若分阶段）

1. **P0**：后端 **inbox + 已读** + 发送方 **写入一条记录**。  
2. **P1**：登录/前台 **拉取 + 心连心列表展示未读**。  
3. **P2**：**本地 1～2 日跟进通知** + 已读取消排程。  
4. **P3**：回前台节流、聚合多条关怀为一条通知摘要。

---

## 7. 小结

| 维度 | 结论 |
|------|------|
| **产品** | 非实时、偏「回访提醒」，应用**诚实文案**可接受。 |
| **技术** | **可行**；后端需新表新接口；客户端复用现有通知栈。 |
| **与实时推送** | 本方案**不替代** C 档推送；后续可并存（推送即时 + 本方案作补充或降级）。 |
